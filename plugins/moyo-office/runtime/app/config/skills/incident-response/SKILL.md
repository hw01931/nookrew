# 장애 대응

## 단계
1. 판단: 심각도, 영향받는 기능·사용자.
2. 공유: 상황 공유문 초안.
3. 완화: 한 조치와 시각 기록, 해결 확인.
4. 사후 분석: 시간순 정리, 근본 원인, 후속 조치.
어느 단계인지 모르면 먼저 묻는다.

## 심각도
| 등급 | 기준 |
| --- | --- |
| SEV1 | 서비스 중단, 모든 사용자 영향 |
| SEV2 | 주요 기능 저하, 많은 사용자 영향 |
| SEV3 | 작은 기능 문제, 일부 사용자 |
| SEV4 | 겉모습·영향 적음 |

## 사실만 쓴다
- 아는 것, 한 것, 다음 할 것만. 추측은 "가설"로 표시한다.
- 시각·로그·경보는 기록(record.search, 사용자가 준 로그)에서 가져온다. 시간표를 지어내지 않는다.
- 외부 조치(재시작·롤백)의 결과를 확인하지 못했으면 "결과 미확인"이다. 직원은 운영 시스템을 직접 조작하지 않는다.
- 로그를 옮길 때 비밀 키·토큰·개인 정보는 지운다.

## 상황 공유문

```
## 장애 공유: [제목]
심각도: SEV? | 상태: 조사 중 / 원인 확인 / 관찰 중 / 해결
영향: 누가·무엇이
마지막 갱신: [시각]
### 현재 상황
### 한 조치
### 다음 조치와 다음 공유 시각
### 시간순 기록 (시각 · 일)
```

## 사후 분석(비난 없이)

```
## 사후 분석: [제목]
날짜 · 지속 시간 · 심각도 · 상태: 초안
### 요약 (2~3문장)
### 영향 (사용자, 기간, 확인된 업무 영향)
### 시간순 기록
### 근본 원인
### 다섯 번의 왜 (증상 → … → 근본 원인)
### 잘된 점 / 아쉬운 점
### 후속 조치 (내용 · 담당 · 우선순위 · 기한)
### 교훈
```

사람이 아니라 시스템과 절차에 집중한다. 확인되지 않은 원인은 "추정 원인"으로 쓴다.

## 결과
공유문·사후 분석은 artifact.write type report. 후속 조치는 work.write로 업무를 만들고, 원인 코드 수정은 debug 스킬을 따른다. 재발 방지 교훈은 memory.write로 남긴다.
