# 배포 점검표

## 원칙
- 점검 항목의 상태는 근거가 있을 때만 체크한다. 검사 결과는 check.run이나 검증 기록, 승인은 사용자 기록. 근거가 없으면 "미확인(NOT_RUN)"이다.
- 이 앱의 직원은 실제 배포를 하지 않는다. 점검표·되돌리기 계획·배포 순서를 문서로 만들고, 실행은 사용자가 한다.
- 되돌릴 기준은 배포 전에 정한다. 배포 중에 정하지 않는다.

## 조사
- 바뀐 것: change.read로 수정안, record.search로 관련 업무·결정.
- 데이터 형식·저장 위치가 바뀌는가(project.search로 마이그레이션·스키마 파일), 설정·환경 변수가 바뀌는가, 외부 API 계약이 바뀌는가.

## 점검표(artifact.write type report로 저장)

```
## 배포 점검: [이름] · [날짜]
### 배포 전
- [ ] 등록된 검사 통과 (근거: 검증 기록 ID)
- [ ] 수정안 검토·승인 (근거: 기록 ID)
- [ ] 알려진 치명적 문제 없음
- [ ] 데이터 변경을 복사본으로 시험함 (해당 시)
- [ ] 이전 데이터를 새 버전이 읽을 수 있음 / 새 데이터를 이전 버전이 망가뜨리지 않음
- [ ] 설정·비밀 값 준비 (값은 문서에 쓰지 않는다)
- [ ] 되돌리기 방법 문서화와 백업
### 배포
- [ ] 시험 환경에 먼저 배포하고 확인
- [ ] 핵심 사용자 흐름 확인(무엇을 눌러 무엇이 보여야 하나)
- [ ] 운영 배포 후 오류·속도 관찰(얼마 동안)
### 배포 후
- [ ] 지표 정상
- [ ] 변경 기록·안내 작성
- [ ] 관련 업무 정리
### 되돌릴 기준
- 오류율 [사용자가 정한 값] 초과
- 응답 시간 [값] 초과
- [핵심 흐름] 실패
```

## 상황별 추가
- 데이터 구조 변경: 백업, 되돌리는 방법(되돌릴 수 없으면 명시), 큰 표는 시간 추정.
- 기능 켜고 끄기(플래그): 기본값, 끄는 법.
- 호환이 깨지는 API: 사용하는 쪽 목록과 안내 순서.
- 모바일: 스토어 심사 기간, 이전 버전 사용자 호환.

## 결과
점검표(report), 배포 순서가 길면 type flow나 diagram(flowchart). 결정이 필요한 것(되돌릴 기준 값 등)은 decision.write로 제안한다.
